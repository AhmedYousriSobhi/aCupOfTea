CLAUDE.md

Working rules for the repository maintainer: the organizational-phase scope, structure-versus-content rule, naming, git flow, Docsify navigation and validation checklist.

Repository

aCupOfTea — a personal knowledge base covering AI, machine learning, software engineering, programming, business, and applied projects. Published as a Docsify site: .github/workflows/deploy-docs.yml deploys main to the gh-pages branch on every push. Day-to-day work lands on dev first (§11).

Repository organization is governed by SPEC.md. Read it before making any structural change.

1. Primary Role

Act as a Senior Knowledge-Base Architect + Repository Maintainer. Keep the repository logically organized, discoverable, consistent, scalable, maintainable, and correctly navigable both on raw GitHub and on the rendered Docsify site.

2. Current Development Phase

Organizational improvement phase. The concern is structure, taxonomy, naming, navigation, placement, cross-references, and Docsify wiring — not content quality. Do NOT assume existing content needs improvement.

3. Critical Rule: Do Not Modify Content

Unless explicitly requested, do NOT: rewrite documents · correct technical explanations · rewrite notebooks · refactor code · change algorithms · modify project behavior · update examples · remove content because it looks outdated · combine documents because they look similar.

structure  → may change
content    → stays unchanged

If content looks problematic, report it separately — don't fix it.

4. Before Making Organizational Changes

  1. Read SPEC.md.
  2. Inspect the current repository tree (and .docs/_sidebar.md/.docs/_navbar.md).
  3. Identify the artifact's primary purpose.
  4. Determine its category (SPEC.md §3).
  5. Check for an existing canonical location for that knowledge.
  6. Check references/links pointing at it, including Docsify navigation entries.
  7. Make the smallest coherent structural change.

Never reorganize based on filename alone.

5. Classification Model

Classify by primary purpose: Concept · Technology · Engineering · Problem · Project · Experiment · Business · Reference · Decision (see SPEC.md §3 for the full table and examples).

6. Project Rule

Projects are first-class artifacts. Never move a project under a technology folder just because it uses that technology — cross-reference instead.

7. Naming Rules

New names use lowercase-kebab-case. Avoid camelCase, PascalCase, mixed casing, misspellings, unexplained abbreviations. Don't rename an existing path without a structural reason — and if you do, fix every reference to it (relative links, root-absolute links, and absolute github.com/AhmedYousriSobhi/aCupOfTea/blob/main/... URLs).

Kebab-case applies to directories and `.md` pages. Code, notebook, and data files (.py, .ipynb, .csv, ...) keep their names: Python modules can't be kebab-case, and notebooks/scripts reference each other and their data by filename. README.md stays README.md.

Write internal links root-absolute (/fields/benchmarks/hpl.md). They resolve on both GitHub and Docsify (relativePath: false); ./ and ../ links break on the site. Images are the exception: Docsify prepends the page's folder to root-absolute image paths, so link images relative to the page (images/name.png, in an images/ folder next to it).

8. Directory Rules

Avoid unnecessary depth. Before creating a directory ask: "Does this represent a durable, meaningful distinction?" If not, use an existing category or an index file instead.

9. Duplicate Prevention

Never duplicate substantive knowledge across categories just to make it visible from multiple places. Prefer one canonical document + a cross-reference from the folder README.md index.

10. Moving Files

Prefer git mv old/path new/path. After moving:

  1. Search for references to the old path (including relative Docsify links, which are path-sensitive).
  2. Regenerate navigation: cd .docs && ./gen_sidebar.sh && ./gen_navbar.sh, and commit the result.
  3. Update internal/relative links.
  4. Check case-sensitive path changes.
  5. Verify original content was preserved byte-for-byte.

11. Git Safety

Before: git status. After: git status, git diff --stat, git diff. Don't mix unrelated changes into a structural migration. Avoid destructive Git operations unless explicitly requested.

Branching flow: feature branch → dev → main.

  • Cut every feature branch from dev, one branch and one PR per feature, and open the PR against dev.
  • Never push or open PRs directly to main. main only receives changes through a dev → main PR.
  • Pushing to main redeploys the public site, so merge the dev → main PR only when the owner approves the release.
  • Before opening the `dev → main` PR, run python3 .docs/tools/update_recent.py and commit the README on dev: it writes the "Recently added" list (the newest pages added, from git history) so GitHub shows it too. The release PR's CI fails if it is stale. The site fills the same block itself at deploy time.

12. Root Directory

Keep the root clean: README.md, SPEC.md, CLAUDE.md, LICENSE (CC BY 4.0, content), LICENSE-CODE (MIT, code), .gitignore, and Docsify/CI infra (index.html with the page shell and styles, its Docsify settings in .docs/config.js, .docs/ holding the sidebar/navbar and their generators, .github/, .gitmodules). .nojekyll is created by CI at deploy time. No temporary notes, experiments, or project-specific files at the root.

13. README and Docsify Navigation

README.md files are primarily navigation documents (purpose, structure, links, related projects) — but the root README.md also doubles as the Docsify homepage, so keep it welcoming, not just a bare index.

.docs/_sidebar.md and .docs/_navbar.md are generated from the file tree by .docs/gen_sidebar.sh / .docs/gen_navbar.sh (thin wrappers around .docs/tools/gen_sidebar.py / gen_navbar.py, which read each page through .docs/tools/pagemodel.py: front matter by PyYAML, the first # heading, the label rules), which CI re-runs on every push to main. Never hand-edit them: CI overwrites manual edits. To change the site's navigation, change the structure, the page's # H1 heading (used as its label), or the generator. After any structural change, regenerate them locally and commit the output so the repo matches what CI publishes.

Site search is .docs/search.js (loaded from index.html, replacing Docsify's built-in search): an overlay (about 720 px wide, full screen on phones) opened by the search icon in the top bar, the side-menu search box, / or Ctrl/Cmd+K. Results come in three groups: page-title matches, passages inside pages and code, narrowed by chips for type, level and domain; with nothing typed it shows the page read last, recent and saved pages. It is built from the pages listed in the generated sidebar, so new pages are searchable with no extra step. On the deployed site it loads two prebuilt files (written by stage_site.py via build_search_index.py, not committed): .docs/index-titles.json (title, summary, type, level, domains, tags, reading time; about 29 KB gzipped, loaded when the search opens and precached for offline) and .docs/index-body.json (the text of every section and the fenced code, about 1 MB gzipped, loaded on the first search for text, not precached); for a local preview (docsify serve of the repo) run python3 .docs/tools/build_search_index.py --local first (the two files are git-ignored); without them the overlay says the index is not built (there is no in-browser crawl).

The site runs on Docsify 5.0.0, pinned in index.html. Three abandoned Docsify 4 plugins were replaced by small scripts of ours, so there is nothing left to break on its own: .docs/theme-toggle.js (a theme list: Auto, Light, Sepia, Dark, Midnight, Black, and a text size row with four sizes that set --font-size; the dark stylesheet is Docsify's own addon, each theme's colours are one block in index.html, the choice is saved in the browser and Auto follows the device), .docs/sidebar-groups.js (menu folders open and close, and the folders of the current page open by themselves, also after a search result, with the current entry marked and scrolled into view) and .docs/page-outline.js (the "On this page" list at 1400px and wider; narrower screens get the section list in the menu). Docsify 5 reads its colours from --color-bg, --color-text, --border-color and --theme-color; the site styles use those same names (the older --background, --textColor, --borderColor and --accent aliases are gone). All site CSS is in .docs/site.css (self-hosted fonts first, the page, then the search overlay), linked from index.html; on the deployed site stage_site.py also joins the local scripts that load before Docsify into one .docs/site.js (each file in its own try, same order), while the repo's index.html keeps them separate so a local preview needs no build. The previous Docsify 4 version is the last commit on main before the upgrade release, if a rollback is ever needed.

Browser smoke test: .docs/tests/smoke.js opens the staged site in headless Chromium at a desktop and a phone size and checks the menu, a long page and its images, search, the page footer, the 404 page, formulas, diagrams, alerts, phone table cards, the phone image viewer, the theme button, sideways scrolling, script errors, a small accessibility scan (names on links and buttons, alt text, field labels, unique ids, page language, a main landmark) and a page-weight budget (scripts, styles, fonts and data of a first home-page visit, uncompressed; pictures are only reported). smoke-test.yml also keeps the staged site as a build artifact (7 days) so a reviewer can open it without building. smoke-test.yml runs it on PRs that touch index.html or .docs/. CI runs it twice, in Chromium and in WebKit (the engine of every iPhone browser); each check name starts with the engine. Locally: python3 .docs/tools/stage_site.py --out _site && node .docs/tests/smoke.js _site [chromium|webkit] (needs the playwright package; WebKit also needs playwright install-deps on Linux).

Every script and stylesheet in index.html is pinned to an exact version and carries an integrity hash (the browser refuses a file the CDN changed), and so are the two libraries loaded only on demand: Mermaid and KaTeX are fetched by .docs/lazy-libs.js only on a page with a diagram or a formula. .docs/tools/check_pins.py compares the pins (in index.html and .docs/*.js) with npm's latest (the monthly workflow check-pins.yml prints the table in its summary and fails on a deprecated package). After bumping a version, run python3 .docs/tools/check_pins.py --sri --write to update its hash (the monthly run also checks the hashes still match, and test_check_pins.py fails in CI on a CDN file without one). Bump pins deliberately, one at a time, and re-check the site in a browser. GitHub Actions in the workflows are pinned to a commit hash with the version in a comment (uses: actions/checkout@<sha> # v4.4.0), because a tag can be moved to other code; .github/dependabot.yml proposes the updates as PRs into dev.

On phones (up to 768px) a tap on a page image opens it large in a pan-and-pinch layer (.docs/image-viewer.js, loaded from index.html); desktop keeps Docsify's zoom-image plugin.

On phones, tables with 2-4 columns show each row as a card and wider tables scroll sideways (.docs/phone-tables.js adds the classes, the CSS is in index.html); desktop is unchanged.

Code files and notebooks linked from a page (/folder/script.py, /folder/notebook.ipynb) open as readable pages on the site: Docsify asks for script.py.md, and stage_site.py writes that file in the staged copy (.docs/tools/code_pages.py: the source highlighted; a notebook's text, code, outputs and output pictures, with links to GitHub and Colab). Link code files root-absolute like pages; nothing else is needed.

index.html sets a Content-Security-Policy (a <meta> tag, since GitHub Pages cannot send headers): scripts only from the site and cdn.jsdelivr.net, no inline scripts (so a script injected into a page cannot run; put any new script in a file under .docs/), styles from the site, the CDN and inline (inline styles stay because Mermaid, KaTeX and <noscript> use them), fonts only from the site (.docs/fonts/, self-hosted, OFL) and the CDN (KaTeX), pictures from anywhere over https, no plugins, and frames only from this site (frame-src 'self', used by the embedded labs below). A new script, style or font host must be added to the policy, or it is silently blocked (Docsify's own vue.css imports Google Fonts: that request is blocked on purpose and --font-family-mono is set in site.css instead); the smoke test fails on any violation (it ignores one harmless eval probe in docsify-pagination).

Interactive labs: standalone pages in a labs/ folder next to the series they belong to (fields/data-science/probability-statistics/labs/: HTML, one shared lab.css and lab-core.js, one script per lab; vanilla JS, no libraries, no inline scripts, each page with its own strict CSP meta). A page shows a lab inline with a link written [text](/folder/labs/name.html#embed ':ignore'); .docs/lab-embed.js turns it into a card (the lab's name, an "Open the lab here" button and an "Open full screen" link): the sandboxed frame is built only when the reader opens the card, or when a link such as quick-guide.md?id=<lab heading> points at the heading above it (the script keeps that heading in view while frames above it grow). A page lists its labs in front matter (labs: [name]; validate.py checks that the file exists and the page has the link) and the deployed page shows "Interactive lab: ..." under the title; put the card in a ### Try it: <the lab's question> section with what it shows and a starting preset. Each lab has a one-line scope (.scope, shown when it is framed) and its first breadcrumb is the story page that embeds it (a lab page opened on its own redirects there via that link, unless ?standalone=1; GitHub shows the plain link). Security rules, all required: the path must match <folders>/labs/<name>.html (allowlist in the script) and resolve to this site's own origin; the frame is sandbox="allow-scripts" without allow-same-origin (an opaque origin: no access to the page, its storage or cookies; no top navigation, popups or forms), referrerpolicy="no-referrer", lazy; messages are accepted only from a frame the script made (origin "null"), the height is clamped to 240-3000 px and nothing from a message is ever inserted as HTML; the lab reads only ?embed=1&theme=light|dark. A lab must work with storage and the parent blocked (wrap localStorage in try/catch). Never add allow-same-origin, allow-top-navigation or allow-popups to the sandbox, and never widen frame-src; the smoke test checks the sandbox, the frame address, the blocked parent and storage access, and that no frame is blocked by the policy.

Code blocks are coloured by Docsify's Prism; index.html adds the Prism language files the pages use (bash, python, powershell, yaml, c, ini, sql). A new fence language needs its prism-<lang>.min.js added the same way (then check_pins.py --sri --write).

On phones the top menu is one 52px row that stays on screen: a labelled "Menu" button (Docsify's own toggle, moved to the top-left) then Home (and Categories at 400px and wider), with the search icon and the theme button (themes and text size) at the right end; External is left out there (the side menu ends with "Source on GitHub") and the first line of a page sits 16px under the bar (the smoke test checks the single row, the gap and the overlap at 390px); the GitHub corner is hidden there and the side menu ends with a "Source on GitHub" link (.docs/config.js). The side menu starts with "🎲 Surprise me", which opens a random content page from the menu (not folder indexes or generated pages; .docs/surprise-me.js). Under it, .docs/reading-history.js marks the menu entries of pages already opened in this browser with a small check and shows "▶ Continue: <title>" for the last page read, and a "Save for later" button under each title feeds a "Saved" list in the menu (localStorage only, nothing sent; no storage means nothing is kept). A page in a learning path ends with "Part 2 of 6" and a Next button, and Start here shows "2 of 6 read" with the next unread step under each path (.docs/generated/paths.json, written by generate_index.py). The theme menu has Export and Import: the history and saved pages as one JSON file, to move between devices. Pages longer than two screens get a thin reading-progress bar at the top and a back-to-top button (.docs/reading-progress.js); the bar is green while you read the page and a muted grey for the blocks added at the end ("See also", "Mentioned in", the footer), so green reaches 100% where the page text ends. The window is the page's scroller: index.html uses overflow-x: clip, not hidden, on html, body (hidden would make <body> scroll instead, and window scroll events would stop), and pins the top menu with position: fixed.

When a page's Markdown cannot be fetched (a dropped connection), Docsify would show an empty page headed "0 -"; .docs/load-error.js replaces it with "This page could not be loaded", asks for the file once more and says what happened (answers after all and reloads once, 404, a server error, or the connection failed) with a Try again button (the smoke test aborts one page request and checks it). Images after the first on a page are lazy-loaded (.docs/lazy-images.js adds loading="lazy" before the page is inserted), so long pages fetch pictures as you scroll.

The glossary is references/glossary.md (one ## TERM section per acronym, starting with the expansion in bold; status: draft until the author has corrected it). On the deployed site stage_site.py links the first use of each term on a page to its entry, with the expansion as the hover text (.docs/tools/glossary_links.py): exact case-sensitive whole words only, never in code, headings, links, tables, HTML, math, folder indexes, a page whose title names the term, or a term in parentheses right after its expansion. Sources are never rewritten. To add a term, add its section to the glossary.

Pages read once can be read again offline: stage_site.py writes sw.js (a service worker) into the root of the staged site from .docs/sw-template.js, versioned with the git commit so each deploy gets a fresh cache (older ones are deleted). It caches the shell (index.html, its scripts, the menu files, the search index, the pinned CDN files) on install, then answers same-origin requests network-first and the CDN cache-first. .docs/offline.js registers it on https or localhost only, and only when sw.js exists, so a local docsify serve of the repo is unaffected. On a page inside a folder of 3 to 80 pages .docs/offline-series.js adds "Save this series for offline": it fetches every page of the folder and their pictures so the worker keeps them (shown only when a worker controls the page). No sw.js is committed (root stays clean, §12).

The homepage has a "Recently added" block between <!-- recent:start --> and <!-- recent:end --> in README.md; stage_site.py fills it at deploy time with the newest added pages from git history (renames do not count), and the committed file keeps the empty markers. The same step builds the deployed homepage from README.md (the source is unchanged): one H1 with the tagline under it, the logo from .docs/icons/logo.png instead of GitHub's attachment host, a Search button and a "Continue" link (.docs/reading-history.js), and page counts in the menu table.

A line that is only $$...$$ is shown as a display formula with KaTeX (.docs/math.js, KaTeX loaded by lazy-libs.js); inline $...$ and anything inside code fences is left alone. Pages stay plain LaTeX, which GitHub also renders.

Every content page ends with "Edit this page" (the file on GitHub, branch dev) and, on the deployed site, "Last updated" (.docs/page-footer.js). The dates come from .docs/last-updated.json, which stage_site.py writes from git history (so the deploy checkout uses fetch-depth: 0); a local preview shows only the edit link.

.github/CONTRIBUTING.md is read on GitHub, not on the site (the home page links to its GitHub page), so its screenshots and links are root-absolute (/.github/images/x.png, /SPEC.md): GitHub resolves them against the repository root in both the file view and the repository's Contributing tab, where a relative images/x.png or ../SPEC.md breaks. Docsify would double the folder, which is why the guide is not rendered on the site.

Folder README convention (best practice): a folder README.md is the start of that folder: a one-line purpose, then ## Contents with a | File | Description | table for pages and a | Directory | Description | table for subfolders, one short description per row. A README that is itself a topic page (a single question, a project) is content, not an index, and is left as written. new_page.py adds each new page's row (or a link in a bullet list).

Generator behavior worth knowing: folders without any .md page are skipped; git submodules (not checked out in CI) are rendered as external links to their repositories; a folder's README.md is not listed as a child: the folder's heading in the menu is the link to it (the chevron folds the group); a non-README page titled Overview is listed first. SPEC.md is not listed at the root: the menu ends with an "About this site" group holding it and a link to the contributing guide.

New pages: create them with python3 .docs/tools/new_page.py (steps in .github/CONTRIBUTING.md; the code is split into page_scaffold.py (paths, taxonomy, front matter, the check), page_index.py (folder README rows, navigation) and page_prompts.py (the questions), with new_page.py holding --adopt, --update and main; tests that move the repo root set new_page.sc.ROOT). It picks the folder and kebab-case file name, writes front matter (id, title, type, domains (suggested from the folder's pages), optional summary, level, tags from .docs/metadata/taxonomy.yaml, prerequisites and related), adds the row to the folder README.md table, and regenerates the sidebar and navbar. Front matter is hidden on the site by Docsify's official front-matter plugin; keep YAML comments out of it. For a page written by hand, new_page.py --adopt PAGE adds the front matter and index link without touching the text; --update PAGE changes the metadata of a page that already has some. Reading time is never asked: new_page.py --check PAGE shows it once the page is written, with what is still missing.

14. Ambiguity

When classification is uncertain: STOP. Don't silently make a judgment call. Report:

Artifact:
Current location:
Possible classifications:
Recommended classification:
Reason:

If the ambiguity materially affects the architecture, ask the user.

15. Structural Changes — Report Format

For any non-trivial reorganization, report:

Before — current relevant tree Findings — structural problems found Target — proposed structure Migration — old/path → new/path, one line per item Docsify Impact — how the generated sidebar/navbar change Validation — checks performed (§16)

Keep migrations minimal and reversible.

16. Validation Checklist

Before finishing:

[ ] No unintended content modifications
[ ] No accidental deletions
[ ] No broken internal links
[ ] Sidebar/navbar regenerated; every entry resolves
[ ] No duplicate canonical artifacts
[ ] Naming is consistent
[ ] Project boundaries preserved
[ ] Directory depth reasonable
[ ] Root remains clean, Docsify infra intact
[ ] Navigation (folder README indexes + generated sidebar) is accurate
[ ] SPEC.md remains accurate
[ ] CLAUDE.md remains accurate
[ ] git status contains only intended changes

17. Do Not Over-Engineer

Don't reorganize to look architecturally sophisticated. Prefer simple + consistent + scalable over deep + granular + theoretically perfect. The repo should be navigable without understanding its entire taxonomy up front.

18. Content vs. Structure

Always distinguish a structural issue ("ML notes live under an inconsistent directory") from a content issue ("this explanation of gradient descent is wrong"). During organization-only work: fix the first, report the second — don't touch it.

19. Agent Decision Hierarchy

SPEC.md → existing taxonomy → artifact's primary purpose →
consistency with neighboring artifacts → long-term scalability → minimal migration cost

Don't optimize for the shortest path alone.

20. Final Principle

Every artifact should answer: What is this? Why does it exist? Where should similar things go? How can I find it later — on GitHub, and on the Docsify site?

If the repository can't answer those through its structure, improve the structure — don't compensate with more content.

21. Metadata Layer

An optional overlay on top of the folder structure: pages can carry YAML front matter so they are discoverable by domain and tag and linked to related pages. Folders remain the primary location; files never move for metadata's sake. Pages without front matter are valid ("legacy").

  • Schema and controlled vocabulary: .docs/metadata/schema.yaml, .docs/metadata/taxonomy.yaml. Add a new domain/tag there before using it.
  • Tools: .docs/tools/cupctl.py (cupctl <verb> <action>, one kubectl-style entry point that runs all the scripts below; cupctl alone lists the commands), .docs/tools/check_all.py (the whole suite, see below), .docs/tools/validate.py, check_links.py, update_recent.py, check_pins.py, test_new_page.py, generate_index.py, stage_site.py, optimize_images.py (Python + PyYAML 6.0.2; Pillow 12.0 optional, for image recompression); page_gui.py (new_page.py --gui) is the same authoring flow as a local browser form; suggest_subjects.py (issue #198: suggests subjects and related pages for a title and summary by text similarity, from the generated objects.json; new_page.py prints the suggestions at the Subjects and Related questions and the form shows them as chips to click; --pair A B and the warning about two subjects that are not marked as related give the evidence for a pair: pages that carry both and the words they share; --evaluate checks it on the repo's own pages); page_doctor.py turns their warnings into a to-do list for the changed pages (open at the line, suggested fixes; also stale .docs/generated, pictures without a description, swapped folder READMEs, and an optional pre-push hook).
  • Generated output (never hand-edit, deterministic): .docs/generated/ — JSON indexes plus Explore pages. Commit it with the change.

Add metadata to a page — put front matter at the very top of the file, nothing else changes:

---
id: sequence-models            # explicit, unique, kebab-case; required if the page has or receives relations
title: Sequence Models
order: 3                       # optional: reading position inside the folder (1 = first)
summary: How models handle ordered data like text, from RNNs to transformers.   # optional, one line, max 200 chars
level: intermediate            # optional: beginner | intermediate | advanced
type: concept                  # concept | guide | reference | note | problem | project | experiment (definitions in taxonomy.yaml); one, or a list of two: [concept, guide]
status: stable                 # draft | stable | deprecated
domains: [deep-learning]       # from taxonomy.yaml
tags: [rnn]                    # optional, max 5, from taxonomy.yaml
relations:                     # optional; targets are explicit ids
  prerequisites: [deep-learning-basics]
  related: [encoder-decoder-machine-translation]
---

Front matter may be partial: every field is optional (defaults: title = first H1, type = note, status = stable); id is needed only for pages that take part in relations. sidebar_label overrides a page's label in the generated sidebar without touching its heading (one line, warned over 40 characters, unique within its folder, quoted if it contains :). order (a whole number from 1 up, unique per folder) puts a page at that position in its folder: the generated sidebar lists a folder's README first, then pages with an order in that order, then the rest alphabetically, and the Previous/Next buttons, the "Read next" strip and Start here paths follow it; give every page of a series an order instead of renaming files (validate.py errors on a duplicate and warns when a page comes before its own prerequisite in the same folder). labs (optional list of lab names, labs/<name>.html in the page's folder or above, each embedded on the page with #embed) adds an "Interactive lab" line under the page title on the deployed site. sidebar_group (on a folder's README.md only) names that folder's group in the sidebar instead of the text before the last hyphen in its H1; use it when sibling folders would otherwise share a group name. Same limits as sidebar_label. A page that carries only these fields is not indexed.

Reading time is computed (200 wpm over the body, code excluded), never authored. summary and level feed the Explore lists and the Start here page (learning paths from prerequisites, quick reads of 10 minutes or less, beginner picks); prerequisites must not form a cycle.

Choosing domains and tags

  • Domains describe the subject, not the folder. Most pages need one or two; three is the most (a convention: validate.py warns above it). The domains of one page should go together: each domain lists the ones it goes with in related in taxonomy.yaml (a pair is listed once and read both ways), and validate.py warns when two domains of a page are not related. If a page truly spans two areas, add them to each other's related list.
  • A kind of page (type) that is not in taxonomy.yaml can be added there (new_page.py and the form ask, or --new-type KEY=DESCRIPTION); a new subject created for a page is marked related to the page's other subjects.
  • A deep-learning page does not also get machine-learning unless it teaches general ML.
  • LLM pages may carry both generative-ai and natural-language-processing.
  • tabular-data is a folder, not a domain: pages under fields/tabular-data/ default to machine-learning and statistics (recorded under folder_defaults in taxonomy.yaml).
  • A tag needs 2+ pages, or must name a concrete technology (kind: technology in taxonomy.yaml). Max 5 tags per page; the validator errors above that and warns on single-use tags that are not marked as technology.
  • Merge, don't multiply: prefer an existing tag (for example gpu covers CUDA, clustering covers segmentation) over adding a near-duplicate.

Rules: no YAML comments inside front matter (gen_sidebar.sh reads the first # line as the page label); the path-derived fallback id of legacy pages is never a relation target; relations never target git submodule content (submodules are skipped entirely).

After any change, before pushing — one command runs the whole validation suite and applies the generators:

python3 .docs/tools/check_all.py --fix   # then commit what it updated

check_all.py runs validate.py (0 errors), check_links.py (0 broken links), regenerates .docs/generated, _sidebar.md and _navbar.md (--fix keeps the result; without it a stale file fails the run and nothing changes on disk) and every test_*.py. A new test_*.py is picked up with no wiring. The steps still work alone (validate.py, check_links.py, generate_index.py, cd .docs && ./gen_sidebar.sh && ./gen_navbar.sh).

Summary health check: a summary is optional but recommended, so a page without one is never an error or a warning. validate.py counts it instead: it prints summary coverage: N of M content pages (P%) (folder README.md indexes with a ## Contents list are not counted), check_all.py shows the same line as [info], validate.py --list-missing-summaries lists the pages still without one, and --summary-coverage prints just the line. test_summary_coverage.py covers it.

CI (validate-metadata.yml) runs on PRs to dev/main and pushes to dev, and runs check_all.py (without --fix), so it fails on validation errors, broken internal links, raw HTML that would run in readers' browsers (<script>, <iframe>, <object>, <embed>, on...= handlers, javascript: links outside code; check_links.py, a deliberate case needs <!-- allow-html --> on the line before), or a stale .docs/generated, sidebar or navbar, or a failing test. check_links.py also warns, one line per page, about pictures without a real description (![], ![image], a file name as the description); the warning never fails CI and --no-alt-report silences it.

Deploy: CI builds a staging copy (stage_site.py --out _site) that also writes a share page for every content page at its folder address (share_pages.py: that page's title and summary as Open Graph tags, then the page's text as static HTML (prerender.py, a small Markdown renderer: headings, text, lists, tables, code, links and images; raw HTML and math are left out) so search engines and readers without JavaScript get it, and a redirect to the #/ page by .docs/prerender-redirect.js, a script file because the CSP forbids inline scripts, and not a meta refresh because crawlers treat that as a redirect and skip the text; --base-url sets the public address, default the GitHub Pages site), so a pasted link shows that page's own preview (each share page also gets a 1200x630 picture, card.png next to it, with the site name, folder, title and summary, drawn with Pillow by .docs/tools/social_cards.py; without Pillow the site icon is used); the page footer's "Copy share link" copies that address. The staged copy also gets sitemap.xml (the home page and every content page at its share address, with its last commit date), feed.xml (Atom: the 30 newest pages added, with title and summary; index.html advertises it) and robots.txt naming the sitemap (.docs/tools/feeds.py). The copy also strips front matter, puts a page header on every content page but the homepage and folder indexes with a ## Contents list (a breadcrumb above the title; under it a meta line "Intermediate · Guide · 6 min read · Updated 13 Nov 2026", tag chips and a one-line "Read first / Read next" strip of at most two links each), puts "See also" with summaries at the end of the page, then "Mentioned in" (the pages that link to it, up to 8, from their root-absolute links; folder indexes and the page itself do not count; .docs/tools/backlinks.py), drops a hand-written "Table of contents" (or a bare list of links to the page's own sections) from the staged copy only, and publishes that copy. In that copy it also writes a lossless WebP next to each PNG (.docs/tools/webp_images.py: kept only when smaller and pixel-identical; the PNG stays as the fallback file), points each local page image at it and gives it its width and height (Docsify's ':size=WxH', so the page does not jump while pictures load; images with a title, in code fences or remote are left alone), and recompresses PNG and JPEG images losslessly (.docs/tools/optimize_images.py, Pillow pinned in the deploy and smoke-test workflows; a file is replaced only when the result is smaller and pixel-identical, and the step is skipped when Pillow is missing). The copy leaves out the local form's page (.docs/tools/page_gui.html, listed in LOCAL_ONLY in stage_site.py) and __pycache__ folders: they do nothing on the public site. Sources are never rewritten. A local docsify serve of the repo hides the front matter on the page (Docsify's front-matter plugin) and in search (.docs/search.js strips it), but does not show the Related block; to preview the deployed result run python3 .docs/tools/stage_site.py --out _site and serve _site/ (git-ignored).

22. Testing Claims in a Throwaway VM, and Checking Newer Releases

When a page states how software behaves (a kernel interface, a systemd setting, a scheduler option) and nobody has run it, test it before release instead of trusting memory or docs alone. Docs and recollection were wrong in places in the memory-pressure series; a VM run caught them.

The VM trick: run the checks inside a throwaway VM that is destroyed afterwards: up → run a checks script inside it as root → destroy, with the revert in a trap so it runs even when a step fails. Ask the owner to guide you to the VM setup (where it lives, which box or image, which provider); don't assume a path or reuse an existing lab VM.

  • Ask the owner before running; it starts a VM and may touch libvirt or other host state.
  • Use a new folder and a new VM, never the owner's existing lab VMs.
  • Record the host's VM and network state before (for libvirt: virsh list/net-list/pool-list/vol-list, vagrant box list) and diff it after. vagrant destroy can delete a pre-existing persistent libvirt network: re-define it if so. The cached box stays.
  • Write checks that print real output and prove the failure path too (ordinary user refused, limit hit, process restarted). A bare wait returns 0 whatever the job did: capture each exit code directly.
  • Put the result on the page: what was run, on which distro and kernel, and what differed from the docs. Anything not run stays marked "untested".

Check newer releases too. Testing on one release (say Ubuntu 22.04, Linux 5.15) is only half the answer. Before release, also find what changed in the recent releases of the same thing (say Ubuntu 26.04, Linux 7.0): features added, defaults changed, behaviour fixed or removed. Use release notes, the kernel/systemd/package changelogs and the current man pages, and for each item either add it to the page (with the version it appeared in) or note that the page still holds. A "Versions" table (see fields/system-administration/linux-memory-pressure/README.md) is the place for it. Then test the interesting differences on a VM running the newer release when you can.
