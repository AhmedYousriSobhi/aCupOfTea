The Changelog Nobody Reads: What Moved Between Slurm 23.11 and 26.05

A per-topic tour of what changed in Slurm between 23.11 and 26.05 for preemption, jobsubmit/lua, reservations, signals, accounting and cgroups, with the security-fix timeline and upgrade paths.

Part of the [schedulers](/fields/schedulers/slurm-intro.md) directory. This page was assembled from SchedMD's changelogs and release notes, read through a web fetch and summarized, so it quotes short lines and names the version each one belongs to. Nothing here was run: the tested pages in this directory ran on Slurm 23.11.4, and the sources and coverage section says exactly what was and was not read. For a real upgrade, read the official notes for every version you cross.

The config that survived three upgrades

A site has a slurm.conf that was written in 2023. It has been copied to every new cluster since, with the care people give to a recipe from a grandmother: nobody remembers why each line is there, and nobody dares remove one. This autumn the admin plans to move from 23.11 to 26.05, because the old version stopped getting fixes, and checks the plan by reading the one page everybody reads: the install guide.

Nobody reads the changelog. It is long, written by developers, and mostly about things that do not apply to you. The few lines that do apply are scattered across five releases: a default that changed, an option that was renamed, a path that now has a different name. Each is harmless to know in advance and annoying to discover on a Monday.

This page is those lines, collected by topic.

The security timeline

Security fixes did not wait for 26.05. They arrived as point releases on the branches that were supported at the time:

FixWhere it appearsWhat it was
CVE-2024-4251124.05.2, with matching releases on 23.11 and 23.02Access control around network and IMEX channel resources in the HPE Slingshot and NVIDIA IMEX switch plugins
CVE-2024-4893624.05.4A stepmgr flaw that could let an attacker execute processes
CVE-2025-4390424.05.8, 24.11.5, 23.11.11, 25.05.0A coordinator could add a user with elevated privileges
Eight CVEs, including CVE-2026-65107 to 65109, 65138 to 65140, 65165 and 6516826.05.4, 25.11.8, 25.05.9sbcast credential checks, a slurmstepd stack overflow, OCI cleanup deleting files outside its directory, a malformed-RPC heap over-read, unsafe cluster names reaching accounting queries, and an operator editing Administrator accounts

Two things follow. First, 23.11 did receive security releases, up to at least 23.11.11 for the privilege issue above. A cluster still on 23.11.4, like the test cluster behind these pages, is missing even those. Second, the 2026 batch was released for 26.05, 25.11 and 25.05. The announcement does not say whether 23.11 or 24.x are affected. It lists those three branches as fixed, so an older branch is not going to receive them, whether or not it is affected. Whichever version you run, take the latest point release of a supported branch.

Preemption

VersionChange
24.05"For PreemptMode=CANCEL and PreemptMode=REQUEUE assume that job signalled for GraceTime was preempted." A job that is signalled during GraceTime and then leaves is recorded as preempted
24.05.4A fix for QOS preemptability being lost after clearing a preempt list with preempt=''
25.05A new PRIORITY preemption option so that a preemptor can preempt only when its priority is higher than the victim's. Deleting a QOS now removes it from the other QOSes' preempt lists
25.05.1, 25.05.5preempt/partition_prio no longer lets a partition's PreemptMode default to PRIORITY. A fatal error when min_exempt_priority was not the last PreemptParameters option was fixed
26.05PreemptExemptTime now also applies to PreemptMode=suspend,gang under preempt/partition_prio. Partitions can be created or updated dynamically with PreemptMode=Priority. A segfault with QOS SUSPEND on an OverSubscribe=YES partition was fixed in 26.05.3

What this means for the preemption pages: the 24.05 line affects how a victim that exits cleanly during GraceTime shows up in sacct. On 23.11 that was not tested here. The GraceTime signal behavior itself (the early SIGTERM reaching steps and not the batch shell) was measured on 23.11.4 only, and none of the changelogs read mention it, so it needs a rerun on the version you use.

job_submit/lua

VersionChange
24.05.2curr_dependency is exposed in job_submit.lua and jobcomp.lua
24.11job_desc gains assoc_qos, and there is a slurm.get_qos_priority() function. burst_buffer/lua loses slurm.job_info_to_string()
25.05.3A controller crash was fixed when a script read job_desc.assoc_qos for an association that does not exist
26.05A Lua stack trace is logged on runtime errors in slurm_job_submit() and slurm_job_modify(). core_spec and thread_spec are exposed in job_desc
26.05In partition definitions Exclusive=[NO|NODE|USER|TOPO] replaces ExclusiveUser and ExclusiveTopo

The Lua page says a broken script is hard to debug. From 26.05 a runtime error leaves a stack trace in the log, which makes the failure-mode table there easier to use. The assoc_qos field in 24.11 is a candidate for a stronger version of Recipe 1: the script could check which QOS the user's association really allows before routing to high_<account>. That idea was not tested.

Reservations

VersionChange
24.05USER_DELETE lets users with access to a reservation delete it. In 24.05.4 nodes in reservations with the Maintenance or Overlap flags are considered when new reservations are created
25.05FORCE_START lets recurring reservations start in the past. Empty reservations can no longer be created with ANY_NODES. Typed GRES reservations work without also listing the untyped GRES. sacct gets a ReqReservation field
25.11New reservation access controls, AllowQOS and AllowPartition
26.05"Do not allocate maintenance nodes to new reservations." FLEX plus MAGNETIC reservations can pick up jobs that extend past the end (26.05.2)

The maintenance page was tested on 23.11.4. The maintenance-flag behavior in 24.05.4 and 26.05 is about picking nodes for a second reservation, which that page did not exercise. The ReqReservation field is useful for the sacct question "did this job ask for a reservation?".

Signals and killing jobs

VersionChange
24.05The default for UnkillableStepTimeout became 60 seconds, and an error is logged when it is less than five times MessageTimeout
25.05"Sigkill user processes atomically by using cgroup.kill interface"
26.05"KillWait will be honored when the task does not end with the TERM signal." srun --ignore-signals stops specified signals being forwarded to tasks. After a task returns a non-zero code, SIGCONT, SIGTERM and SIGKILL go to the remaining tasks. Job cancellation is no longer delayed while slurmstepd is launching a task (26.05.2)

The signals cheat sheet measured the KillWait and SIGKILL timing on 23.11.4 with a task that ignored SIGTERM. The 26.05 KillWait line is exactly about that case, so those timings are the first thing to rerun with the probe. The kill-task-failed page is also affected by the UnkillableStepTimeout default.

Accounting, sacct and sacctmgr

VersionChange
24.05Output, error and input paths are stored in the database and shown by accounting tools
24.11sacctmgr ping checks slurmdbd. sreport gets AccountUtilizationByQOS
25.05sacct can show TimeLimit and TimelimitRaw for steps, and SegmentSize
25.11Administrators can change a job's AllocTRES retroactively through sacctmgr. slurmdbd.conf gets DisableArchiveCommands
26.05sacct --json and --yaml print submit_line for steps and a .jobs[].sluid field. A fix in 26.05.4 for corrupted earlier accounting records (a bumped requeue counter and a missing start time)
26.11 (development)"Record the name, not the UID, of the user that cancelled a job or set a node reason."

The last row matters for the sacct page: on 23.11.4 a cancelled job showed CANCELLED by 30033, a numeric user ID. If the 26.11 change ships as described, the same record would carry a name. The -D view of a requeued job is also the one the 26.05.4 fix is about.

cgroups

VersionChange
24.05CgroupPlugin=disabled, SystemdTimeout= in cgroup.conf, RestrictedCoresPerGPU, and a requirement of dbus 1.11.16 or newer for cgroup v2
25.05"cgroup/v1 started its deprecation process", with a recommendation to move to v2. EnableExtraControllers is added to cgroup.conf
25.11slurmd can be launched in a cgroup slice other than system.slice
26.05cgroup v2 paths are built from the SLUID instead of the numeric job ID. 26.05.2 adds an option to use the job ID again, and the default stays SLUID

The cgroups page already covers the 26.05 path change. The 25.05 deprecation is the one to plan around, because a cluster on cgroup v1 will want to be on v2 before a later release removes v1. No removal was found in the notes read here.

Back to the config that survived three upgrades

Replay the plan with this page open. The admin reads the changelog entries for each hop, and ends up with a short list instead of a surprise. The cgroup v1 deprecation goes on the calendar. The UnkillableStepTimeout default is noted, because the old value would be changed under them. The tested pages' claims get a Friday afternoon rerun on a test controller, with the probe from the signals page, and the three that differ are written down.

None of it is dramatic. The upgrade happens on a Saturday, the config line nobody remembered is still there and still harmless, and Monday is dull in the way upgrades should be.

Takeaway: security fixes came as point releases on supported branches, so the goal is the latest point release of a supported version, not a particular major one, and the changes worth knowing are small and scattered (GraceTime and KillWait handling, Exclusive=, cgroup v1 deprecation, SLUID paths), so read each hop's notes before you cross it.
